# Dataset provenance

## Summary

**Every case in this repository is synthetic.** No real patient data, no
de-identified real patient data, and no restricted dataset is used, required,
downloaded, or committed here. No generative model is involved in producing any
case (see [Generative models](#generative-models) below).

Two benchmark artifacts ship here, with different provenance:

| Artifact | Provenance | Version | Cases | Produced by |
|---|---|---|---|---|
| `synthetic/benchmark_v1.json` | Hand-authored | `v1` | 10 | `app/benchmark/curated.py` |
| `synthetic/clineval-benchmark-v0.1/` | Programmatically generated | `clineval-benchmark-v0.1` | 100 | `app/benchmark/synthesizer.py` |

### How cases are generated

Ground-truth-first. A structured synthetic case is built, and the note,
reference summary, and annotations are each rendered **independently** from it:

```
structured case ──> clinical timeline ──> source note
                                     └──> reference summary
                                     └──> structured annotations
```

No text is written first and back-annotated. Full methodology in
[docs/BENCHMARK.md](../docs/BENCHMARK.md).

### How the seed works

Each case is seeded with `"<master_seed>:<index>"`, so its content is fully
determined by the master seed, its index, and the configuration.

```bash
python -m scripts.generate_benchmark --cases 100 --seed 42
```

Running this twice produces byte-identical files, across processes and machines.

### What is deterministic

**Deterministic** — given the same `--seed`, `--cases`, and configuration:
every case's content, its difficulty tier, the note text, the reference
summary, every annotation, every entity id, and the difficulty distribution
(allocated by largest remainder, so the realized mix matches the configured mix
exactly rather than only in expectation).

**Not stable across a changed case count.** Difficulty tiers are allocated
across the whole run, so `--cases 200` reassigns tiers and does **not**
reproduce the first 100 cases of a `--cases 100` run. Reproducibility is scoped
to the full `(seed, case_count, config)` triple.

**Varies** — only the timestamp in `metadata_*.json` (`generated_at`).

### Generative models

**None.** No LLM, no language model, and no learned component is used to
produce any part of any case. Notes, summaries, and annotations are all
produced by deterministic Python renderers reading a structured object. The
content library in `app/benchmark/content.py` is hand-curated.

This matters for the benchmark's credibility: ground truth generated by a
language model would be ground truth no more trustworthy than that model.

## 3. What the content is

Fictional and written to be *clinically plausible* so the benchmark
meaningfully exercises an evaluator. The library holds 18 conditions, 31
medications, 16 laboratory analytes, and their linkages — a condition knows its
typical medications and the labs usually followed for it, which is what keeps
generated cases coherent.

It is **not** medical reference material, **not** a description of any real
person, and **not** reviewed by a licensed clinician.

Timing is always relative — "3 months ago", "on hospital day 2" — never an
absolute calendar date. Patient identifiers are synthetic surrogates
(`SYN-PT-00042`). There are no names, dates of birth, addresses, contact
details, or record numbers, and an automated check asserts their absence on
every case.

## 4. Verifying these claims

The integrity checks are executable, not just documented:

```bash
python -m scripts.audit_benchmark
```

This recomputes every statistic directly from the cases (rather than trusting
the metadata file), runs all integrity checks including the
no-identifiable-information scan, and exits non-zero on any failure.

## 5. Synthea

Synthea is named in the architecture as a possible source of realistic
structured patient timelines in later phases. As of Phase 2 it is **not** used,
and no Synthea output is committed here. When it is used, those cases will
carry `DataProvenance.SYNTHEA_DERIVED`, and generated text will still not be
treated as ground truth on its own — the gold-standard layer will remain
independently derived from structure.

## 6. Restricted datasets (MIMIC-IV-Note and similar)

The system is architected so a credentialed user could point it at a restricted
dataset **locally**, on their own infrastructure, under their own data use
agreement. To be explicit:

- Restricted data is **never** downloaded by this project.
- Restricted data is **never** committed to this repository.
- Restricted data is **not required** — everything runs on the committed
  synthetic benchmark.
- Obtaining credentials and complying with the relevant data use agreement is
  entirely the responsibility of anyone who chooses to do this.

## 7. Limitations

**Synthetic cases are not equivalent to real clinical documentation.** They are
cleaner, shorter, more structured, and more internally consistent than real
notes. They lack the abbreviations, dictation errors, copy-forward accretion,
institutional templates, and genuine ambiguity of real records. Sentence
structures repeat across cases, so a model could learn surface regularities
that would not transfer.

Coverage is not representativeness: 20 failure modes across 100 cases exercise
20 failure modes. They do not represent the distribution of real clinical
documentation, nor of real summarization errors.

Results on this benchmark describe behavior **on this benchmark**. They are not
evidence of real-world clinical performance, and subgroup slices are
benchmark-level analysis only — not evidence about real-world population
fairness.

## 8. Intended use

Evaluation and research on AI summarization behavior. Not for clinical
decision-making, not for training models intended for patient care, and not as
a source of medical information.
